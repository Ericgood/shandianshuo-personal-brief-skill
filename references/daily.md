# 源头研究、推荐账与每日运行

每次源头研究同时读[增量采集、事件去重与反馈校准](collection-and-calibration.md)：记录分页/缓存/部分读取回执，原文与事件分层去重，真实反馈与模型判断分开，校准接入本轮及现有每周复盘。原始信源仍是主流程，AIHOT仅补充发现。

## 第一次运行的持久设置

settings.json保存用户选择：reference_days、timezone、daily_time、身份确认/跳过及当前需要、当前profile路径/状态/最后完成run、schedule的宿主/任务ID/回查时间。首次先按[访谈](onboarding.md)确认身份（已填也核实是否仍准确），完成分析后立即产出当日报告，再设置后续日程；首轮不等待日程触发。不要把公开仓库或其它用户的画像当默认值。已有旧档案可导入引用，但必须先核实其完成审计、实际覆盖和当前授权；未完成档案不能冒充可信全量输入。

偏好权威正文默认在原生资料库library/个人信息偏好.md，settings.profile.path记录实际路径。已有outputs画像完整迁入后保留旧文件作历史档案，不同时维护两个版本；先完整读已有资料库文档，保留用户修改，保存后验证原生资料库可见。每次先读最新明确反馈和该文档完整语义正文。覆盖各类兴趣目录，再按候选找细节，不能只召回最像职业的主题。近期任务有日期/过期条件，旧事项无结案不代表仍待办。

## 每日跟上新需要，每周复盘稳定判断

三层是信号的用途；远期/中期/近期是证据时间，两者不能混为一套标签：

| 文档内容 | 更新节奏 | 允许怎样影响推荐 |
|---|---|---|
| 稳定偏好 | 每7天系统复盘，谨慎调整 | 持续提供候选方向；结合既有跨期证据与反例，不凭本周次数重排整个人 |
| 近期需要 | 每日增量理解完成后更新 | 今天或昨天明确提到的具体需要即可参与当天源头发现和排序，不等待周更 |
| 新观察候选 | 每日保存新证据 | 可作少量相关探索；一次提及、密集排障或连续出现都不自动升级长期兴趣 |

本人明确的身份变化、喜恶和纠正立即覆盖相应旧判断，无需等复盘；仍区分用户确认与模型推断。新任务未形成稳定兴趣，也可以有很有用的推荐，不能用“尚未确认长期偏好”阻挡即时相关性。

每日先完整处理自上次成功run以来授权范围内全部新增/修改记录，再更新profile的近期需要/候选部分。特别检查以用户时区计算的今天和昨天的已读记录，识别真实本人需求及任务；代写、引用、虚构和反复故障分别处理。漏跑后的补读不能只限最近两天，修改的旧记录也不能误称今天新说的话。

对当前需要寻找有实际帮助的原文，而不是只复述用户刚说过的主题。推荐理由可将已核实的需求日期与文章价值联系起来，概括即可；不直接引私人转写或关系细节，不把这些内容带进公开查询。没有新记录或没有合适原文，就回到其他有效偏好；不要求每天必须出现一条“昨天说过”的内容。

settings记录profile.recent_updated_at与profile.stable_reviewed_at。首次完整建档初始化两者；每日增量合并成功后只更新近期时间与analysis.last_completed_run，不把它算作稳定层已复盘。每日任务计算距stable_reviewed_at是否满7天，满则在同一任务中复盘，不另建周期任务。缺旧时间时先查已有审计，无法确认则记录未知并做一次有依据的初始复盘，不假设今天刚完成过。

每周复盘读取既有稳定偏好、明确反馈、上次复盘后全部已读归纳和候选证据，联同既有跨期支持判断持续、加强、淡出、冲突或临时任务；不是只读最后7天，也不再重传一年原文。首次建档/增量覆盖不全就先补齐，不让不完整证据悄悄改变稳定层。模型提议仍标候选，用户确认状态保留。稳定层及复盘记录保存成功才推进stable_reviewed_at；失败留待重试，原稳定层仍可用且明确截至时间。

## 整份日报的选题与信息增量

默认容量10条，质量不足时少给；用户可在settings.recommendation_policy调整数量与配比，明确专题请求优先。条目数增加不能成为放宽来源与证据门槛的理由。近期需要每日更新只表示及时进入候选，不能据此承包整份日报。

先读完整偏好目录与最近7天推荐曝光，再安排不同方向的候选预算，不能先搜最热近期任务，再拿剩余名额补长期兴趣。默认10条参考分配：长期持续关注4、中期正在形成的方向3、近期具体需要2、邻近探索1；不足10条时仍保留长期和非工作方向，不机械凑比例。这里是推荐服务的目标，不是文章发布日期，也不是将远中近期证据机械分栏。每条指定一个主要用途用于计数，可关联多个偏好；不得把同一语音问题改贴长期/中期标签充数。

生活、小说、游戏、人物日常等为横向内容维度：10条中争取至少2条有依据、质量达标的非工作内容，计入上述总数，不额外占位。没有新记录不等于没有持续兴趣；没有可靠内容应记供给缺口，并继续从相应原作者补源，不能用更多同主题技术新闻填空。

候选广召回覆盖至少5个不同兴趣方向；按完整画像里的较大兴趣领域核对覆盖，不能把同一职业领域的技术细分当作生活、创作或娱乐的替代。内容用途由实际主题与个人价值决定，不能只因访谈适合放松听就算非工作内容。同日修订选题时，可以明确保留已推荐的优质条目参与重新配比，不重复记为新推荐；跨日仍遵守去重与信息增量要求。预算允许时收集约30—50个候选，仅把有潜在价值的正文读深。按来源可信度、个人价值、时效与实质增量筛选，再按整份清单的互补性取舍，而不是给单篇打分后简单取前10。近期高频是任务强度的证据，不能单独成为推荐价值分。

除URL去重外，给候选记录topic、need_cluster、主要用途、生活/工作维度、回答的具体问题、独有信息与证据。聚合前先问：读了上一条以后，这一条能新增什么判断或动作？同一事件、同一问题的替代解法与相似观点通常合成一条主推荐，互补链接作延伸阅读；一个条目不是靠塞入十篇文章绕过容量。通常同主题最多2条，同作者/机构优先1条；独立反证或明确不同的决策价值可例外，但写出理由。语音克隆、配音API、变声GPU、声音榜单若都为同一供应商选择服务，属于一个需求簇，不能因技术名词不同拆成4条。

### 跨日重复与有理由的重荐

旧文章第一次推荐不算重复；文章发布日期与用户上次收到的日期分开。推荐前查看全部已有原文记录，并重点比较最近30天的原文、转载/视频与文字等同一内容、事件结论和具体问题；最近7天再检查主题曝光强度。同主题不等于同内容：新的独立实测、反证或不同问题可以有价值，换作者复述相同结论则仍冗余。借鉴[MMR](https://www.cs.cmu.edu/afs/cs/Web/People/jgc/publication/MMR_DiversityBased_Reranking_SIGIR_1998.pdf)同时考虑个人价值与相对已曝光内容的信息增量，不假装实现了未经验证的向量模型或精确分数。

30天是默认避免重复的观察窗口，不是论文证明的通用最优值，也不是到期自动重发。相同原文平时跳过；30天内更谨慎。只有以下有证据的情况才重荐：原文有实质更新；用户新出现的具体需要使旧文有新的用途；用户明确要求重看/复习。不同原文的新证据通常作为新条目说明与旧推荐的关联，不冒充同篇重荐。高分、仍然相关、没点击、标题改了、重新发现或只过了30天都不足以构成理由。已明确看过且无新增价值的内容不主动重推。

重荐应醒目标“重荐/进展”，写上次推荐日期和报告链接、这次新增事实或用途及证据；旧日期未知就明确未知。默认每日报告最多留1个重荐位置且无须用满，这是可校准的编辑默认值；用户明确要求专题追踪或复习可例外。同日修订的“保留”另计，不增加一次曝光或伪装新推荐。无值得重荐的理由就补其他方向或少给，不能为了填满十条放宽门槛。

内容账保留每次推荐事件，不覆盖第一次或最近一次时间；记录reason、previous_run_id、rationale、evidence、disclosure，与研究/抓取时间分开。每次日报记录新推荐、重荐、同日保留及排除的近似重复数，推荐与用户已读仍分开。7天/30天复盘结合明确反馈和实际样本检查重复率与信息增量，不因用户未点击猜测喜恶。

报告先给可扫描的简短目录，每条正文围绕一个有用结论，说明原作者背景、为什么适合、日期与阅读范围。推荐是帮助理解、创作、享受或决策，不要求每条都变成工作待办。运行账记录实际用途分布、主题/需求簇分布、非工作条数、合并数及未覆盖原因；配比是结果质检，不是虚构精确评分或固定人格标签。

用户当轮主动说“关注谁/想看什么”的新增与取消，按[user-updates.md](user-updates.md)即时处理；每日先合并这些明确要求与待核实状态，再安排搜索预算，不重复首次访谈。

## 来源发现从用户出发

1. 根据身份、持续兴趣、当前需要和少量探索，找原作者、作品或机构入口。不存在一份对所有人都适用的固定125源榜；原作者访谈、文学、游戏、生活需求也可在AIHOT外补源。
2. 用原站About、作者自述、署名和近期原文确认“是谁、做什么、主要写什么”。职务日期未知、自述或只有转载时明确标注。作者、所属公司和承载频道分开，同公司工程博客和PR不硬合并，同名不借用他人履历。
3. sources.json为每个来源保留稳定ID、作者/机构身份与平台别名、更新入口、背景证据URL、内容倾向、个人推荐理由、模型暂定分和用户分、样本、首次/最近观察、最后成功游标、失败与待续位置。来源分分配预算，不能永久屏蔽低分源中的好内容。
4. 评分高的来源多查，低频来源轮转。预算按用户选择与宿主额度，不硬规定全网每天全文精读；记录实际覆盖、访问失败和未完成窗口。新来源先作候选，证据充分后登记，不靠每天新闻不同就把每条新闻算新信源。
5. 历史研究过、推送过和用户读过分开。没有明确反馈不能用未点击判断不喜欢。

对产品/公司关注项，同时检查[user-updates.md的官网与创始人覆盖表](user-updates.md#官网与创始人渠道覆盖)。官网、官方频道与创始人个人频道分开轮询与记游标；身份核实不等于动态已读，缺口继续补，不把官网作为唯一来源。

## AIHOT可选发现入口

先读取实时 [OpenAPI](https://aihot.news/openapi-v1.json)。2026-10-13核对时，公开全部动态接口为：

```text
GET https://aihot.news/api/v1/items?mode=all&window=7d&by=timeline&limit=100
```

响应items与page.hasMore/page.nextCursor；使用真实opaque cursor分页，不自行构造。首轮可查48小时并多读一页跨边界；后续从最后成功扫描起保留时间重叠，按已见ID辅助去重。timeline对回填/迟收录有规则，跨过收录时间边界不保证全部延迟项；标注实际窗口与局限。7天之外接口不保证保留。cursor绑定滚动查询，下一日从首屏开始，不盲复用过期cursor。

Cache-Control作为最短轮询间隔，保留ETag可用时If-None-Match；429/503遵守Retry-After。页数/时间预算到了就保存未完成位置与窗口，不声称全量。先前错误把page字段当顶层hasMore会漏分页，因此核对响应结构而非凭旧实现猜测。

API摘要/分数只用于宽召回；个人偏好先决定查哪些原始入口，不能只重排站点精选。保留AIHOT归属及原文URL。来源目录不完整就说明，不把站点自报数量当验证覆盖。个人非商业使用与对外商业产品授权不同：[线上使用条款](https://aihot.news/terms)。本Skill代码MIT不授予资讯/文章转载权，也不代替AIHOT线上授权。

## 内容与事件账

Agent把公开候选写入 outputs/personal-brief/candidates.json：

```json
{"items":[{"url":"https://example.org/article","title":"公开原文标题","source_id":"S001","published_at":"2026-01-01","body_read_scope":"listing_only","event_id":null}]}
```

在工作区根：

```text
node <skill-dir>/scripts/state.mjs ingest candidates.json
node <skill-dir>/scripts/state.mjs status
```

state输入路径相对于outputs/personal-brief；原文从多个源出现会合并source_ids，保留原推荐状态。helper只做URL归一（去追踪参数/片段、明确X原帖别名），不按标题硬合并，不擅自移除有语义的查询参数，不把相似话题全删。内容正文阅读、事件归组和真实信息增量由Agent负责，记录其证据。

阅读后用文件工具更新对应item的body_read_scope/status=researched及事件判断；先读当前账、原子保存，不能和helper并发写。正文指纹可作为转载线索，但HTML模板、菜单和重复展示会污染指纹，不能凭整个页面哈希断言文章相同。

报告先保存reports/DATE.md审计版本，同时将完整正文保存到原生资料库library/每日信息推荐-DATE.md，并更新library/每日信息推荐.md可点击索引；回读核实正文与索引后才记推荐账。保留已有用户编辑；同日重跑用run后缀。资料库保存失败时不声称完整交付、不推进已推荐状态。再写receipt.json：

```json
{"run_id":"实际唯一run","report":"reports/DATE.md","urls":["https://example.org/article"]}
```

`state.mjs recommend receipt.json`检查报告存在且含准确原文URL；最多10条，同run重试幂等。默认拒绝已推荐原文；有理由重荐须在receipt增加repeats数组，每项含url、previous_run_id（账中最近一次）、reason（material_update/renewed_context/user_requested）、rationale、evidence、disclosure（报告中的准确重荐说明）。helper只校验锚点、结构和说明已保存，不能证明理由真实或信息增量充分，仍须Agent按上节判断。它将新事件追加到同一内容的recommendations，保留旧记录；禁止改runID或清空历史绕过。delivery仍是unconfirmed，user_read_status仍unknown。报告保存/文件包含URL的检查不证明推荐内容正确。同日“保留”不放入新推荐回执。

helper以独占锁避免两个写账进程同时修改；崩溃遗留锁时先核实没有活动运行，再由用户/获授权维护处理，不自动删别人的锁。整个每日Agent运行也应使用宿主互斥或工作区run锁：先验证上一轮状态，禁止另一个模型同时覆盖sources/profile/report。源抓取失败不推进源游标，日报保存失败不推进推荐账。

## 推荐、反馈与运行

写0—10条，原发布日期、索引日期和事件日期分开；近期补读不冒充今日新闻。每条保留发布者背景、具体价值和对应远中近期偏好。个人创作/生活轮换，缺内容允许空。未取得正文、视频未播放、仅预览、署名转载和作者自报数字都写明，不按热度断言好内容。

每次runs.jsonl记录runID、开始/结束、档案版本、旧/新分析run、近期层是否更新及截至时间、稳定层复盘是否到期/完成及证据范围、实际源与列表/全文覆盖、失败、API分页窗口、URL重叠数、事件合并依据、已保存报告和通知是否确认。未知费用填未知，不估成零。状态先临时文件再原子替换，避免未知结果盲重试。

明确反馈才更新对应规则，保留旧版本及场景日期。定期根据真实样本复盘有用率/宣传噪声/访问可靠性，样本少不下精确结论；用户分数不被模型自动覆盖。首次全量分析或每日增量中断时持久化进度，说明剩余范围，不发布伪装已完成的个性化结果。
